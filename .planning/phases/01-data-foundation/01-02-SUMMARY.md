## Decisions Made

- **CookieMethodsServer type annotation**: TypeScript strict mode required explicit types for the cookie `setAll` callback parameters. Used `CookieMethodsServer` from `@supabase/ssr` to type the cookie methods object rather than inline parameter destructuring.
- **Hierarchical RLS via subquery chains**: transactions check folio → holder → family → user_id. This is the correct approach for the 4-level hierarchy — no denormalized user_id columns needed on child tables.
- **Grandfathering seed as external script**: The actual NAV data fetch must come from mfapi.in API (external), not hardcoded SQL. The migration file is a placeholder; the TypeScript script does the real work.
- **`(select auth.uid())` in RLS**: Uses subquery form to evaluate auth.uid() once per statement (not once per row) — standard Supabase performance pattern.

## User Setup Required

To complete Phase 1 DB setup:

1. Configure Supabase project credentials in `.env.local`:
   ```
   NEXT_PUBLIC_SUPABASE_URL=https://[your-project].supabase.co
   NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=[your-anon-key]
   SUPABASE_SERVICE_ROLE_KEY=[your-service-role-key]
   ```

2. Push migrations to your Supabase project:
   ```bash
   supabase link --project-ref [your-project-ref]
   supabase db push
   ```

3. Run the grandfathering NAV seed (one-time — do this before Phase 3):
   ```bash
   npm run seed:grandfathering
   ```
   Expected output: 5000+ records seeded from mfapi.in.

|-------|---------|-----|
